# linalg 中的 ElementwiseOpFusion,这是一种在tensor/linalg级别的语义融合,融合的是linalg.generic对象
%0 = linalg.generic ins(%arg0) outs(%init0) {
^bb0(%in: f32, %out: f32):
  %a = math.exp %in : f32
  linalg.yield %a : f32
} -> tensor<4x8xf32>

%1 = linalg.generic ins(%0, %arg1) outs(%init1) {
^bb0(%x: f32, %y: f32, %out: f32):
  %b = arith.addf %x, %y : f32
  linalg.yield %b : f32
} -> tensor<4x8xf32>

融合前提:
1. fusedOperand 不能为空
2. producer 和 consumer 都必须是 linalg::GenericOp
3. producer 必须是 tensor semantics，并且这个 operand 必须是 ranked tensor
4. producer 的所有 loops 都必须是 parallel 它必须是纯逐元素并行 producer
5. 当前 fusedOperand 必须是 consumer 的输入 operand
6. consumer 这个 operand 的 indexing map 结果数，要等于 producer loop 数
7. producer 结果的 indexing map 必须可逆，目前要求是 permutation
8. 如果 consumer 有 reduction loop，融合后仍必须保住所有 loop bound 信息

# propagation 
shape propagation

 IREE 的 shape propagation 本质上是：
优先复用已经显式存在的 dynamic dims，而不是重新推导一遍
ExpandTensorShapesPass负责显示化
tensor<?*?*10>->flow.tensor.tie_shape tensor<?*?*10>{%ARG0,%ARG1}
2. 中间靠接口沿 SSA 继续传播

IREE 真正“传播 shape”的载体，是 ShapeAwareOpInterface，不是一个全局求解器。接口定义在 UtilInterfaces.td (line 984)。

这里最重要的是两个方法：
getOperandDynamicDims
getResultDynamicDims
也就是说，一个 op 如果知道自己输入/输出的动态维是谁，就直接把这些 SSA 值交出来。
围绕这个接口，IREE 有几组通用 helper：
findDynamicDims：沿 use-def 链往上找已有的 dynamic dims；如果遇到 ShapeAwareOpInterface、SizeAwareOpInterface、TiedOpInterface 就继续追，见 UtilTypes.cpp (line 679)。
buildDynamicDimsForValue：先尝试复用现成 shape SSA；复用不到，再问 ShapeAwareOpInterface；最后实在不行才回退插 tensor.dim，见 UtilTypes.cpp (line 796)。
buildOperandShape / buildResultShape：把“静态维 + 动态维 SSA”重新拼成完整 shape，见 UtilTypes.cpp (line 870)。

flow.tensor.tie_shape 本身不会被“翻译成某个 resource op”，而是先被读出里面的 dynamic dims，塞进 stream.tensor.import/export、stream.tensor.sizeof、stream.tensor.dispatch 这些带 shape 元数据的 Stream op，最后 tie 自己会被清掉。

executable 里面的 flow.dispatch.tie_shape 怎么办
在 executable 内部，flow.dispatch.tie_shape 最终会变成 stream.binding.subspan 上的动态维绑定，而不是保留 tie op。

encoding propagation
也就是它只想把这种：

%cast = tensor.cast %src : A to B
%enc = iree_encoding.set_encoding %cast : B -> B_with_encoding
改成：

%enc = iree_encoding.set_encoding %src : A -> A_with_encoding

affinity propagation
主要是通过 affinityAnalysize
先把 IR 中所有和 affinity 有关的位置注册成 value producer / value consumer / op / global 四类分析节点，再把显式 affinity、pinning、SSA use-def、tied values、CFG、call/return、global load/store 这些关系变成依赖，最后用 DFX solver 做固定点迭代，求出每个位置的可能 affinity 集合。

tied operand propagation
某个 op 的 result，不是全新独立值，而是和某个 operand“绑定/对应/继承”的。于是 operand 上的信息可以传播到 result，或者反过来借 result 的使用情况回推 operand。
dispatch region propagation
常见表现有：

producer 往 dispatch 里 clone/fuse
encoding 往 dispatch 边界推
reshape/transpose 往 dispatch root 附近推
某些 dispatch 外的信息被带进 dispatch
某些 dispatch 内结果关系被 outline 后保留下来
你可以把它理解成：

“让同一段设备计算的值流，尽量在同一个 dispatch 世界里连起来。”

所以它本质上是在传播“dispatch 归属关系”或“适合在哪个 dispatch 边界上表达”的信息。


tensor alias propagation
传播“两个 tensor value 其实可能引用同一底层存储”这件事。

不是说它们一定数值相等，而是说：

可能是同一 buffer 的不同 view
可能是 in-place 更新前后的逻辑值
可能是 slice / subview / alias op 形成的别名链
例如：

%a = ...
%b = tensor.extract_slice %a ...
或者更资源化以后：

%alias = hal.tensor.alias %src ...
编译器会关心：

%b/%alias 和 %a/%src 是否共享底层存储
后续能不能原地更新
哪些 copy 可以省
哪些并发/重排是危险的
所以 tensor alias propagation 本质是在传播：

alias 关系、共享存储关系、非独占所有权关系。

在 Stream 阶段这和：

copy-on-write
copy elision
subrange propagation
resource usage analysis

layout propagation
这就是在传播 layout / encoding。

layout propagation 的目标通常是：

让 producer/consumer 用一致布局
减少中间 layout convert
让 dispatch/codegen 更容易匹配目标 kernel 期望的形式

stream resource propagation
当高层 tensor 值被看成 !stream.resource 之后，编译器继续沿程序传播“这个 resource 是谁、大小是多少、子范围是什么、何时 ready、在哪个 affinity 上、是否是同一底层资源”等信息。

它不只是传播 resource handle 本身，还传播和 resource 并行的一整套附加状态：

tensor -> resource lowering 后，函数签名扩展
block args / iter_args / return 也一起扩展

“逻辑上的一个 tensor 值，到了 Stream 里变成 resource 值后，编译器还得继续把关于这块资源的所有元数据一起传下去。”
