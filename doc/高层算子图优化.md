# Stream层调度与传统后端指令调度、活跃度分析的区别

最核心的一句是：这里做的不是机器指令级调度，而是 **Stream 异步资源操作级调度**；这里的活跃度也不是寄存器活跃度，而是 **resource/timepoint/lifetime 级活跃度**。

## 1. 为什么在这里做调度

前面的 Stream IR 里，虽然已经有很多 `stream.async.*` op，但它们往往还是平铺在函数体中的：

```mlir
%0 = stream.async.splat ...
%1 = stream.async.dispatch ...
%2 = stream.async.transfer ...
%3 = stream.async.dispatch ...
util.return %3
```

这时 IR 还没有明确表达：

- 哪些 async op 应该被看作一组执行单元
- 哪些工作属于哪个 affinity/device
- 哪些结果必须等待，哪些结果可以继续并发
- 后续怎么做 command buffer 形成、resource placement 和 timeline 传播

`ScheduleExecutionPass` 就是在这里把这些“平铺的异步资源操作”整理成显式执行图。

它的直接结果通常会变成：

```mlir
%r, %tp = stream.async.execute with(...) -> ... {
  %0 = stream.async.splat ...
  %1 = stream.async.dispatch ...
  %2 = stream.async.transfer ...
  %3 = stream.async.dispatch ...
  stream.yield %3 : ...
}
%ready = stream.timepoint.await %tp => %r : ...
util.return %ready
```

也就是说，这一步做的是：

- execution region formation
- async boundary construction
- timepoint dependence materialization

而不是把更低层的 CPU/GPU 机器指令换顺序。

## 2. 在这里做调度的好处

### 2.1 执行边界更清楚

把原本平铺的 `stream.async.*` op 包成 `stream.async.execute` 之后，就能明确知道：

- 哪些 op 属于同一个执行 region
- 这段 region 的输入 resource 是什么
- 它的输出 resource 是什么
- 它何时完成，用哪个 `!stream.timepoint` 表示

### 2.2 跨设备执行关系更清楚

Stream 层已经有 affinity/device 概念，因此这里的调度还会按 affinity 切 partition。

多设备场景里，后续会得到类似：

```mlir
stream.async.execute on(#hal.device.affinity<@device0>) ...
stream.async.execute on(#hal.device.affinity<@device1>) ...
```

这样不同设备上的工作不会继续混在一起，transfer 的位置也更明确。

### 2.3 异步依赖显式化

调度前很多顺序关系只是“看 use-def 猜出来的”。  
调度后会显式出现：

- `stream.async.execute`
- `!stream.timepoint`
- `stream.timepoint.await`

这样后续 pass 才能明确理解：

- 哪段工作何时 ready
- 哪段工作必须等待
- 哪段工作还有机会继续并发

### 2.4 为后续 pass 提供稳定执行图

这一步之后，后面这些 pass 才更好做：

- `ScheduleConcurrencyPass`
- `PropagateTimepointsPass`
- `RefineUsagePass`
- allocation / command formation 相关 pass

所以这里的调度不是“为了好看”，而是为了先把执行图的基本结构稳定下来。

## 3. 与传统后端指令调度的区别

### 3.1 调度对象不同

传统后端指令调度调的是：

- machine instruction / MIR / SUnit
- 比如 `load`、`add`、`mul`、`store`

目标是安排 cycle 次序、隐藏 latency、减少 pipeline stall。

而 `ScheduleExecutionPass` 调的是：

- `stream.async.dispatch`
- `stream.async.transfer`
- `stream.async.slice`
- `stream.async.update`
- `stream.async.clone`

这些 `StreamableOpInterface` op。

也就是说，这里的“指令”更像：

- 一个 dispatch
- 一次 resource copy
- 一次跨设备 transfer
- 一段 staging load-store 阶段

而不是 CPU/GPU ISA 指令。

### 3.2 调度目标不同

传统后端 instruction scheduling 主要关心：

- 指令延迟
- functional unit 冲突
- issue width
- pipeline hazard
- 寄存器压力

而 `ScheduleExecutionPass` 的目标是：

- 把可一起执行的 async 资源操作包成 `stream.async.execute`
- 按 affinity/device 切 partition
- 显式化依赖为 `!stream.timepoint`
- 给后面的 concurrency / allocation / command buffer 形成准备 IR

所以它更像：

**任务分组 + 执行域划分 + 异步依赖显式化**

而不是：

**给 ALU / LSU 排 cycle**

## 4. 与传统活跃度分析的区别

### 4.1 活跃度对象不同

传统后端活跃度分析通常看的是：

- 某个 SSA value / virtual register / physical register
- 在某条 machine instruction 前后是不是 live

它主要服务于：

- 寄存器分配
- spill/reload
- dead code elimination
- 调度启发式

而 Stream 这边更关心的是：

- 一个 `!stream.resource<...>` 在什么范围内还活着
- 它的 lifetime 是 `external / transient / staging / constant / variable`
- 它有没有跨 affinity/device 流动
- 它的 byte range 有没有 alias / overlap
- 对应的 timepoint 在哪里 ready

所以它更接近：

- resource lifetime analysis
- use-def + async dependence analysis
- access range / alias analysis
- ownership / placement analysis

### 4.2 典型相关 pass 也不同

在这一层更相关的是：

- `RefineUsagePass`
- `ElideAsyncCopiesPass`

它们关心的不是“寄存器 live range”，而是：

- resource 什么时候必须保留
- 什么时候可以原地复用
- 哪些 `transfer/copy/slice/update` 可以删掉

所以这里的“活跃度”更像 **buffer/resource lifetime analysis**，而不是 register liveness。

## 5. 一个直接对照表

| 维度 | Stream 这里 | 传统后端 |
| --- | --- | --- |
| 调度对象 | `stream.async.*` 资源/dispatch op | machine instructions |
| 粒度 | 粗粒度任务/region | 细粒度单条指令 |
| 依赖 | resource use-def、affinity、timepoint、access range | data dependence、hazard、latency |
| 活跃度对象 | resource / lifetime / alias / timepoint | register / SSA value |
| 目标 | 分区、异步执行、跨设备协调、资源规划 | 提高吞吐、降 stall、控寄存器压力 |
| 结果 IR | `stream.async.execute` / `stream.timepoint.await` | 重排 machine instr 顺序 |

## 6. 一个更贴切的类比

如果一定要类比：

- `ScheduleExecutionPass` 更像 task graph scheduling / command graph formation
- 传统 backend scheduling 才是 instruction scheduling

所以从层次上看，Stream 这里做的是 **异步执行图调度**，不是后端机器指令调度。

## 7. `wave` 的概念

在 `Group concurrently executable work into waves` 这句里，`wave` 不是 GPU 的 `wavefront/warp`，而是 **Stream 调度层里的并发批次/并发层**。

它的语义可以概括成：

- 同一个 wave 内的 async 工作可以同时开始执行
- 一个 wave 的结果 ready 之后，后继 wave 才能继续使用这些结果
- 多个 wave 串起来构成一个执行 DAG

在 IR 里，这个概念通过 `stream.async.concurrent` 表达。

例如，原来 execute 内部可能是平铺的：

```mlir
%1 = stream.async.splat ...
%2 = stream.async.dispatch @dispatch_0(...)
%3 = stream.async.splat ...
%4 = stream.async.dispatch @dispatch_1(...)
%5 = stream.async.dispatch @dispatch_2(...)
```

经过 `ScheduleConcurrencyPass` 之后，可能被整理成两层 wave：

```mlir
%con0:2 = stream.async.concurrent with() -> (...) {
  %splat0 = stream.async.splat ...
  %splat1 = stream.async.splat ...
  stream.yield %splat0, %splat1
}

%con1:2 = stream.async.concurrent with(%con0#0, %arg1, %arg0, %con0#1) -> (...) {
  %dispatch0 = stream.async.dispatch @dispatch_0(...)
  %dispatch1 = stream.async.dispatch @dispatch_1(...)
  stream.yield %dispatch0, %dispatch1
}

%dispatch2 = stream.async.dispatch @dispatch_2(%con1#0, %con1#1)
```

这里可以理解为：

- `con0` 是第一 wave：两个 `splat` 并发
- `con1` 是第二 wave：两个 `dispatch` 并发
- 最后的 `dispatch2` 依赖前一 wave 的结果，因此单独位于后续层

所以 `wave` 更像“执行图中的同一并发层”，而不是底层硬件线程概念。

## 8. 确定执行先后时，支配树和 DAG 的区别

这两者都在表达“先后关系”，但不是一回事。

- 支配树回答的是：在控制流上，谁一定先经过
- DAG 回答的是：在数据/资源依赖上，谁必须先完成

### 8.1 支配树关注 CFG 中的必经关系

如果块 `A` 支配块 `B`，意思是：

从入口到 `B` 的任意路径都必须先经过 `A`。

它主要服务于：

- 判断 SSA 值在后续 block 中是否可见
- 确定跨 block 改写时的安全处理顺序
- 在存在 `cf.cond_br` / `scf.for` 等控制流结构时，保证改写不会破坏支配关系

这也是为什么 `ScheduleExecutionPass` 会先按 dominance order 处理 block。

### 8.2 DAG 关注依赖中的必须先做关系

DAG 更像任务依赖图。  
边 `A -> B` 表示：

`B` 不能早于 `A`。

它关心的是：

- data dependence
- resource dependence
- timepoint dependence
- hazard / alias dependence

所以它更适合做：

- 拓扑排序
- 并发分组
- wave 划分
- 调度划分

### 8.3 在 Stream 调度里的分工

在 `ScheduleExecutionPass` 和 `ScheduleConcurrencyPass` 这层，可以把两者理解为：

- 支配树：外层控制流与 SSA 合法性约束
- DAG：内层资源/执行依赖约束

也就是说：

- 支配树主要决定“按什么 block 顺序改写才安全”
- DAG 主要决定“哪些 async 工作能并发，哪些必须串行”

### 8.4 一个最直接的理解方式

可以把它们类比成：

- 支配树是地图/路网中的必经点关系
- DAG 是任务图中的前驱依赖关系

因此，在真正决定异步工作执行顺序时，更直接起作用的通常是依赖 DAG；而支配树更多用于保证控制流和 SSA 改写的正确性。
